# iOS 长待机屏幕变暗

主界面环境动画继续使用原来的 40 秒保持、4 秒渐停策略。屏幕亮度另由 `IdleScreenDimming` 控制：前台无操作 60 秒后，用 2 秒平滑降到当前亮度的四分之一。最低目标为 0.02，若原亮度更低则保持原值，绝不为省电反而调亮。

这是 `UIWindowScene.screen.brightness` 的实际屏幕亮度调整，不是给界面覆盖黑色图片；系统截图不会记录这项硬件亮度差异。具体功耗改善需要真机测量，不能直接用亮度比例推算耗电比例。

## 行为边界

- 任意触摸开始即恢复亮度，约 0.16 秒完成；同一次触摸继续操作原按钮或拖动，不需要先点一次唤醒。
- 多点触摸、持续按住、拖动、设置页与弹层均由窗口上的被动手势观察器记录。观察器不识别、不阻止、不取消其他手势。文字输入通知也重置闲置时间。
- 录音、识别和上传期间不降亮度，结束后重新计算 60 秒。
- App 失去活跃状态时立即恢复本轮保存的亮度，取消待机任务与未完成渐变。以 `willResignActiveNotification` 加场景生命周期双重清理，避免把低亮度带到控制中心、锁屏或其他 App。
- 若使用者在本轮变暗期间明显调整了亮度（偏离应用写入值超过 0.08 或写入值的一半），应用放弃这一轮亮度所有权，保留新值，不再恢复到旧值。通过 `brightnessDidChangeNotification` 观察，忽略应用自身写入的通知。自动亮度在变暗期间会持续微调（真机上 0.091 读回为 0.096），这类小幅漂移不算接管：早期 0.005 的阈值把它误判为手动调整，导致触摸后不再恢复，且下一轮从已变暗的值继续降低。
- 原有自动锁屏策略不变；本轮仅增加亮度管理。

## 调度与验证

没有增加常驻 `Timer`、显示时钟或周期性轮询。控制器只有一个睡眠至闲置截止时间的 Task；操作更新最后活动时间，截止时按需再睡至新截止时间。渐暗/恢复只在有限的过渡期间以 30 Hz 写亮度，完成后完全停止。动画主时钟不会因为屏幕变暗被重新唤醒。

`scripts/test-screen-idle.sh` 使用注入的亮度读写检查实际控制器，覆盖刷新截止时间、单调渐暗、静止后零写入、触摸恢复、长按与忙碌保护、渐变中切后台、取消后无迟到写入、手动亮度接管和原亮度很低等情况。

`DisplayUITests.testIdleScreenFirstTouchStillOpensSettings` 使用正式的 60 秒截止时间和 2 秒渐变，等待后直接点击设置，检查第一次点击仍能打开页面，再切到后台。控制器状态记录在 `iphone.power` 日志中，结合现有按钮、设备页与录音触摸回归验证窗口观察器没有截断交互。

API 依据：[UIScreen brightness](https://developer.apple.com/documentation/uikit/uiscreen/brightness)、[brightnessDidChangeNotification](https://developer.apple.com/documentation/uikit/uiscreen/brightnessdidchangenotification)。

## 本轮验证记录

- 注入亮度读写的控制器测试通过，验证了目标亮度、平滑恢复、手动亮度接管、后台清理与零待机写入。
- 四项原生 UI 测试通过，包括正式 60 秒等待后的第一次触摸打开设置、录音触摸、结果页开关、显示模式与设备页往返；最终窗口观察器调整后的 60 秒测试另行通过。
- 日志确认波形显示时钟先停止，屏幕管理后进入 dimming、dimmed，触摸后退出，后台变为 inactive。
- 此模拟器的 `UIScreen.brightness` 固定返回 0.500，不能用它验证实际屏幕亮度已降低。UI 测试验证计时与触摸集成，亮度数值/恢复用可注入控制器测试；真机降亮度、自动亮度共存和实际功耗仍需手机验证。
- Debug 模拟器与签名 Release 真机构建通过。
- Release 已安装到现有 iPhone；自动唤起被设备锁定状态阻止，需在手机解锁后手动打开，真机亮度效果尚未观察。
